## Runtime

The native Swift cockpit (`native/`) is the only app in this repo. The old Python/FastAPI backend, its WKWebView shell (`desktop.py`), and its py2app packaging (`build_app.sh`, `setup.py`, `pyproject.toml`) were removed once the native app became feature-complete - see `native/README.md` for build/run instructions.

## Native app (`native/`, Swift + SwiftTerm)

- The sole cockpit surface. Build with `swift build` / run with `swift run` from `native/` (Command Line Tools only, **no Xcode / `xcodebuild`**). First build is ~90s. Full run + captain-validation steps live in `native/README.md`; the authoritative design + verified API shapes are in `data/cockpit-native-design-scout/report.md` (sections 3, 4.3, 5, 6, 7, 9).
- **SwiftTerm is vendored, not a remote SPM dependency** (`native/Vendor/SwiftTerm/`, pinned to upstream 1.15.0 / commit `dd2fb8ac...`; `Package.resolved` no longer exists, since there are no remote dependencies left). This is a deliberate patch, not a stylistic choice: SGR-2 (dim/faint) text rendering (`NSColor.dimmedColor(towards:)` in `Mac/MacExtensions.swift`, mirrored in `iOS/iOSExtensions.swift`) blended a flat 50% toward the background regardless of whether that background was dark or light - fine on dark themes (~4.9:1 contrast) but collapsing to ~2.9:1, nearly invisible, on light ones - and none of `dimmedColor`, `getAttributes`, `buildAttributedString`, or `mapColor` are `open` (nor is `TerminalView.draw(_:)`), so there is no override point from outside the module. The patch (new file `Dimming.swift`) targets a fixed 4.5:1 WCAG contrast ratio against the background via bisection, capped at the original 50% so dark themes render unchanged. See `native/Vendor/SwiftTerm/README.md` for the full writeup and how to re-apply the patch if SwiftTerm is ever upgraded.
- **Second SwiftTerm patch: truecolor de-emphasised text (cockpit-native-fixes5).** The `dimmedColor` patch above only fires for the SGR-2 "faint" attribute - some tools de-emphasise text via a literal 24-bit truecolor foreground instead (`ESC[38;2;r;g;bm`), which carries no theme awareness at all since the child process chose concrete RGB bytes with no idea what background they'd land on. Confirmed live via `tmux capture-pane -e` on a real firstmate session: Claude Code renders its own status lines ("Searched for N files...") as `ESC[38;2;153;153;153m`, not SGR-2 dim - ~6.7:1 contrast on a dark theme (fine) but ~2.55:1 on light (illegible), and `getAttributes`'s `.dim` branch never touches it. `getAttributes` (`Apple/AppleTerminalView.swift`) now also checks `attribute.fg` for the `.trueColor` case and calls the new `NSColor.legibleColor(against:)`/`UIColor.legibleColor(against:)` (`Mac/MacExtensions.swift` / `iOS/iOSExtensions.swift`, backed by `Dimming.contrastFixBlendFraction`), which remaps *any* truecolor foreground that doesn't already meet the contrast floor - self-gating (no-op once contrast is sufficient) and hue-preserving (blends toward whichever of black/white the color can reach the most contrast against, not simply "toward its own background" like the dim patch - that direction has to be chosen by evaluating both endpoints, since a foreground already close to one extreme has almost no headroom left in that direction). See `native/Vendor/SwiftTerm/README.md`'s "Second patch" section.
- **The console** (`main.swift` -> `ConsoleController`) hosts a **dynamic tab collection**, not a fixed two-tab enum. Tabs are `[TabModel]` (`TabModel.swift`), each owning a `CockpitTerminalView` + a `TabLaunch` (re)start recipe, rendered as `TabChipView` chips in a growing tab bar. Supports **new** (`⌘T`/`+`), **duplicate** (`⌘D`, re-runs the same argv), **rename** (double-click / `⌘⇧R` / right-click, name is per-tab and never touches the process), **close** (`⌘W`; closing the last tab opens a fresh shell so the window is never empty), and `⌘1`…`⌘9` select. Tab ops are on the **Tab** menu; zoom+theme on **View**. `ConsoleController.openFirstmateHost()` opens the built-in Shell + Mirror pair; `loadView` calls it at startup so the app still lands there by default, and it is also the pinned Hosts-sidebar entry's connect action (see below). This is Phase 0 of the connection-manager work (design: `data/cockpit-ssh-manager-research/report.md`, Section A4/A5 + D Phase 0). Later phases add the dashboard + embedded backend (P3) and packaging/signing (P4); the console stays backend-free.
- **Navigation shell.** `AppShellController` is the window's root: a fixed, always-visible `IconRailController` (~60pt, icon-only) on the left, and to its right a `TopBarController` (destination title, the Search pill with its ⌘K badge, and the theme-picker button) above a body area. `RailDestination`'s case order (`IconRailController.swift`) drives the rail's top-to-bottom icon order directly - since Swift derives `CaseIterable.allCases` from declaration order, reordering the destinations is a one-line change there (currently `overview, console, hosts, review, settings`, below the sailboat "Home" mark and above the avatar - captain-corrected in cockpit-native-theme-audit-review, overriding fixes4 Fix 2's console/hosts-first order). The body holds all five destinations (`.overview`, `.hosts`, `.console`, `.review`, `.settings`) as permanent children with only `isHidden` toggled - never rebuilt - so navigating away never tears down `ConsoleController`'s running tabs. **`.hosts` and `.console` are decoupled destinations** (cockpit-native-ui-fixes2): `HostsSidebarController` and `ConsoleController` are each a standalone full-size body view, not panes of a shared `NSSplitViewController` - Console shows just the Firstmate Shell/Mirror tab strip, and Hosts is reachable on its own rail icon exactly like Settings. Connecting the pinned Firstmate entry (`HostsSidebarController.onConnectPinned`, wired in `main.swift`) opens its Shell/Mirror pair in the shared `ConsoleController` and calls `AppShellController.show(.console)`. Connecting a *saved* host goes through a sixth kind of destination outside the `RailDestination` enum entirely - see "Dedicated host pages" below. `.overview` shows `FleetController` (see below); `.review` shows `ReviewController` (cockpit-native-theme-audit-review): the same PR data/actions as Overview's "Ready to merge" (`OpenPRsSource.fetch()` + `FleetDataSource.mergedPRs`), grouped by forge instead of merged into one list; `.settings` shows `SettingsController` embedded directly (not a separate window).
- **Per-host pinned rail icons (fixes4 Fix 3).** Below the fixed destinations, `IconRailController.setHosts(_:)` renders one extra icon per saved host (its own icon glyph + accent, tooltip = label; click connects via `onConnectHost` exactly like the Hosts list's Connect). Kept live by `HostStore.observe(_:)` - a list of closures (not a single overwritable `onChange`, since both `HostsSidebarController.reload()` and the rail's `setHosts` need to hear every add/rename/delete) - `main.swift` registers the rail's observer alongside the Hosts panel's own.
- **Dedicated host pages (cockpit-native-host-pages).** A saved host's rail icon (or the Hosts list's own Connect - both call `AppDelegate.connectToHost`, so there is one connect path for a saved host, not two) opens its **own** page: an independent `ConsoleController` holding only that host's ssh tab(s), never the Firstmate console's Mirror/Shell tabs. `AppShellController.connectHost(_:args:)` builds one lazily per host id via an injected `makeHostConsole` factory (so `AppShellController` stays ignorant of `SSHKeyStore`/`SnippetStore`, matching how it already knows nothing about host persistence), embeds it into the shared body container exactly like a fixed `RailDestination`, and keeps it in a `[UUID: ConsoleController]` dictionary for as long as that host stays saved. The dedup fix for the "second click opens a second tab" bug: `ConsoleController.connectSSHIfNeeded` only calls `openSSH` when `tabs.isEmpty`, so a re-click of an already-connected host's icon just re-shows and re-focuses (`focusCurrentTab()`) the existing page - a deliberate second session still needs the tab chip's own Duplicate (`⌘D`). `ConsoleController(opensFirstmateOnLaunch:)` is `false` for these (the shared Firstmate `console` keeps it `true`, its Shell/Mirror pair unchanged). Deleting a host (`HostStore.observe` diffing ids in `main.swift`) tears its page down via `AppShellController.removeHostConsole` (`ConsoleController.shutdown()` + `removeFromSuperview`/`removeFromParent()`), and `applicationWillTerminate` shuts every host console down too (`AppShellController.shutdownAllHostConsoles()`), not just the shared one. None of this is a `RailDestination` case - `IconRailController.activeHostID`/`AppShellController.connectHost` track "a host page is showing" as a separate piece of state from the fixed-destination enum, mirrored on both sides so rail highlighting and body-view switching agree. Tab-menu actions (⌘T/⌘D/⌘W/zoom/theme, wired in `main.swift` with no explicit `.target`) still resolve correctly per page because each host's `ConsoleController` is a real `addChild` in the responder chain - whichever page's terminal is first responder is what the action reaches, exactly like the Firstmate console already worked.
- **Fleet dashboard (`FleetController.swift` + `FleetData.swift`, cockpit-native-ui-fixes2).** The `.overview` rail destination is a real port of `backend/fleet.py`'s `snapshot()` and `backend/openprs.py`'s `open_prs()` into Swift - greeting header, calm/loud answer banner, stat tiles (working/ready-to-merge/queued/done/projects/watcher), an "In flight" list of working crew, and a "Ready to merge" list of open PRs with Review/Merge actions. **No embedded backend**: `FirstmateHome.swift` resolves `$FM_HOME` the same way `backend/config.py` does, then `FleetData.swift` reads `data/projects.md` / `data/backlog.md` / `state/*.meta` directly and shells out to `bin/fm-crew-state.sh` per task (the same authoritative, non-tailed state read the Python backend uses) and to `bin/fm-pr-merge.sh` for the Merge action; `OpenPRsSource` walks `$FM_HOME/projects/*` and re-implements `openprs.py`'s remote-parsing + `gh pr list` + Bitbucket-REST logic natively. `FleetController.refresh()` runs this whole pipeline off the main thread and re-renders on completion - there is no live websocket push (unlike the web app), only a refresh on `viewWillAppear` plus a manual refresh button.
- **Hosts / SSH connection manager (Phase 1, `data/cockpit-ssh-manager-research/report.md` A2/A3, C1, D Phase 1).** `HostsSidebarController` (Termius-proportioned, 220-260pt, list, per-host SF-Symbol icon + Helm accent, quick-connect, add/edit/delete) is its own rail destination (see above); Add/Edit Host is a dedicated full-page window (`AppDelegate.presentHostEditor`), not a sheet on this narrow panel - `HostsSidebarController.onAddOrEdit` forwards the request up through `AppShellController` to the app delegate, which owns `HostEditorController` and the host store. Row zero is always a pinned, non-deletable "Firstmate" entry (anchor icon) whose connect action is `ConsoleController.openFirstmateHost()` - it has no backing `Host` record, so `HostsSidebarController`'s private `HostListRow` enum carries a `.pinned` case alongside `.header`/`.host`. A saved `Host` (`Host.swift`) is `Codable` and persisted by `HostStore` to `~/Library/Application Support/FirstmateCockpit/hosts.json` (override `FM_HOSTS_FILE`) - the native app's first on-disk persistence. **Secrets stay off disk:** `Host.password` is excluded from `CodingKeys` (session-only, memory); the only persisted credential is `keyID`, a reference into the Phase 2 key store below - never a path or key material. **Connect** for a saved host reaches its own dedicated page (see "Dedicated host pages" below) whose one ssh tab runs `/usr/bin/ssh` with the host's argv (the C1 drop-in) plus, when `keyID` is set, a `-i <path>` resolved fresh on every start (see below); the tab takes the host label + accent, and the tab chip's own Duplicate (`⌘D`) re-runs the same launch (re-resolving the key) for a deliberate second session. An ad-hoc quick-connect (`HostCatalog.parseQuickConnect`, no saved `Host` behind it) still opens as a plain tab in the shared Firstmate `ConsoleController` via `ConsoleController.openSSH(...)` directly, since there's no host id to pin a dedicated page to. The Hosts menu's Quick Connect routes through `AppShellController.revealHostsQuickConnect()`, which selects the Hosts destination before focusing it. The topbar Search control is unrelated to Hosts now - see "Find" below.
- **SSH keychain (Phase 2, `data/cockpit-ssh-manager-research/report.md` A1, C3, D Phase 2; Keychain model corrected in cockpit-native-fixes3).** `SSHKey.swift` is non-secret metadata only (label, type, derived public key, fingerprint, certificate), persisted by `SSHKeyStore` to `keys.json` (override `FM_KEYS_FILE`) exactly like `HostStore`. Private key bytes and passphrase live **only** in the macOS Keychain (`KeychainKeyStore.swift`: `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete`), stored with plain `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (never iCloud-synced) - **not** a `SecAccessControl` ACL. That's a deliberate correction, not the original design: on a CLT-only, ad-hoc-signed build (`TeamIdentifier=not set`), `SecItemAdd` with *any* `kSecAttrAccessControl` fails `errSecMissingEntitlement`, confirmed with a standalone probe outside the app - see `KeychainKeyStore.swift`'s file header for the full writeup, including why a `keychain-access-groups` entitlement isn't a fix either (ad-hoc signing it gets the process killed outright, no provisioning profile). The Touch ID / passcode gate is therefore enforced in-app (`KeychainKeyStore.authenticate(context:)` calling `LAContext.evaluatePolicy` before the read), not by the OS ACL - revisit once the app has a real Team ID (Phase 4 packaging). Generation and PEM/OpenSSH import both shell out to `/usr/bin/ssh-keygen` (`SSHKeyGenerator.swift`) rather than reimplementing the OpenSSH key format or its passphrase KDF - `.ppk` files are detected and rejected with a conversion hint, not parsed. `SSHKeyStore.addNew(_:privateKeyData:passphrase:)` is the one path that writes a brand-new key (Keychain first, then metadata) - both the Keys screen and the host editor's inline "+ New Key…" popup entry (`HostEditorController.presentNewKeySheet`, still a sheet - now on the host editor's own window rather than the sidebar's) go through it, so a new key can be created without leaving the host form. At connect time `SSHKeyMaterializer.materialize` does the one Keychain read (the Touch ID prompt) and writes a private `0600` temp file for `ssh -i`; `ConsoleController.connectSSH`/`cleanupSSHKeyTempFile` own its lifecycle (fresh file per tab start/reconnect, deleted on close/exit/quit). The "SSH Keys" browser (`KeysSidebarController.swift` + `KeyEditorController.swift`) is a separate window (Keys menu, `⌘⇧K`/`⌘⇧N`), not a rail destination, and its footer/context-menu Delete action (`SSHKeyStore.delete(id:)`) removes both the metadata and the Keychain items - see `KeychainKeyStore.delete(id:)`. A `swift build`/`swift run` binary has no stable code-signing identity, so Keychain access can prompt again (or rarely fail to re-read) across rebuilds; `native/build_native_app.sh` now codesigns the assembled `.app` with a fixed local identity to keep that identity stable across rebuilds (see the `build_native_app.sh` bullet below and its "Local signing setup" section in `native/README.md`) - not a full Phase 4 Developer ID/notarization setup, just a per-machine local dev cert.
- **Power features (Phase 3, `data/cockpit-ssh-manager-research/report.md` B1/B2/B4/B5, D Phase 3).** All additive `ssh` argv or extra `Host` fields, never new transport code. Jump hosts: `Host.jumpVia` (a saved host's label or a raw `user@bastion`) resolved and chained by `HostCatalog.proxyJumpChain` into `-J a,b,c`. Agent forwarding: `Host.agentForward` -> `-A` (the system agent's `SSH_AUTH_SOCK` is already inherited via `childEnvironmentDict`). Known-hosts prompts: no code needed - `connectSSH` never overrides `StrictHostKeyChecking` and nothing filters the ssh tab's PTY output, so they render like any other terminal output; verified by inspection, not a UI. Groups/tags: `Host.group`/`Host.tags` (present since Phase 1) now drive sidebar section headers and a tag-chip filter row in `HostsSidebarController`. Port forwarding: `Host.portForwards: [PortForwardRule]`, edited via `PortForwardingController` as a sheet on top of `HostEditorController` (a window since the nav-redesign task, not a sheet itself - see above), turned into `-L`/`-R`/`-D` flags. Snippets: `Snippet`/`SnippetStore` (mirrors `HostStore`), managed from `SnippetsController` (Snippets menu, `⌘⌥N`/`⌘⌥P`); Run sends text+Enter to the active tab via `TerminalView.send(txt:)`; a host's `startupSnippetID` fires the same way ~1.5s after ssh starts (best-effort, no "shell ready" signal exists to hook). Session logging: `CockpitTerminalView` overrides SwiftTerm's `dataReceived(slice:)` to tee raw bytes to a `FileHandle` under `~/Library/Application Support/FirstmateCockpit/logs/` - deliberately not SwiftTerm's own `setHostLogging(directory:)`, which splits output across one file per read syscall rather than a single transcript. Toggle via `⌘⇧L`/toolbar icon, or default-on via `FM_LOG_SESSIONS_DEFAULT=1`.
- Every tab is a `CockpitTerminalView` (the P1 paste-hardening `LocalProcessTerminalView` subclass - do not touch its paste override; it is what makes screenshot-paste-into-Claude work). Terminals fork their child **in-process** via `startProcess`, so there is no websocket byte-pump and no per-keystroke round trip.
- **Scrolling:** SwiftTerm 1.15's `scrollWheel` already scrolls normal-screen buffers smoothly and content-wise (accumulates precise trackpad deltas -> whole lines 1:1, no page-jumps; `scrollSensitivity` default 1.0), so shell tabs feel like WezTerm with no extra code. Each terminal gets a **10,000-line scrollback** via `term.terminal?.changeScrollback(...)` (SwiftTerm default is 500). The Mirror tab is tmux on the alt-screen and pages inherently - do not try to force smooth-scroll there.
- The Mirror ports `backend/terminal.py`'s grouped-session lifecycle to Swift `Process` (`TmuxMirror.swift`): same `new-session -d -s <group> -t <session>` / `select-window` / `window-size latest` / `status off` / teardown, same `cockpit_<sess>_<pid>_<hex>` naming. Target is `FM_MIRROR_TARGET`, then Settings > General's "Mirror target" (`AppSettings.mirrorTarget`), default `firstmate`. A crash (not a clean quit) can leave a stale `cockpit_*` group, same tradeoff as the Python version. **Known follow-up:** `setUp` only calls `select-window` when the target names one explicitly (`firstmate:<N>`); with just a session name it inherits whichever window was active in the real session at that instant, so if that happens to be something other than the first-mate pane (e.g. a herdr TUI), the mirror shows that chrome instead. Pin `firstmate:<N>` until there's a real fix - see the doc comment on `TmuxMirror.setUp`.
- **Nine confirmed AppKit gotchas worth knowing before touching tab chips, a scroll view, the host editor form, a dense row layout, or any full-size destination/window root.** (1) `TabChipView.beginRename()` (fixes4) used to call `window.makeFirstResponder(label)` *and then* `label.selectText(nil)` - `selectText(nil)` alone already makes an editable field first responder and starts editing, so the redundant prior `makeFirstResponder` call makes AppKit think a session is already active and needs ending before `selectText` starts its own. That fires a spurious `controlTextDidEndEditing` with the *pre-edit* text right there, permanently flipping the "is renaming" flag false before the user types a single character - the rename UI looks like it's working, but the real commit on Return later hits a now-stale guard and is silently dropped. Root-caused via `Thread.callStackSymbols` inside the delegate callback, not by reading the code. Never call both; `selectText(nil)` is sufficient on its own. (2) `NSGridView` column widths: setting an explicit pixel width on one column (e.g. the field column) while leaving the other unconstrained does NOT make the constrained column absorb extra space on window resize - the *unconstrained* column absorbs 100% of any extra width instead, since nothing else defines where it should stop. That's what caused the "Add Host" form's labels to drift into a growing empty gap as the window widened. Fix: give the column that should *stay* narrow (labels) the explicit width, leave the column that should *fill* (fields) unconstrained, and pin the `NSGridView`'s own width to its container (`widthAnchor.constraint(equalTo: stack.widthAnchor)`) so the fill column has a definite total to fill. (3) A standalone `NSWindow` with `contentViewController` assigned (as opposed to embedded in the shared app-shell body) keeps re-deriving its own frame from its content's Auto Layout fitting size for as long as that content contains a **required equality** chain with no independent lower bound (cockpit-native-host-pages) - not just once at open. Confirmed live (`FM_DEBUG_HOSTEDITOR`-style probe: `setFrame`/`display:true` right after, then read `win.frame` again after a runloop tick): capping-and-centering the host editor's form column with a required `stack.widthAnchor == content.widthAnchor - 48` (paired with a `<=520` cap) made AppKit snap the *whole window* back to 568pt (the one width where that equality has zero slack) within one layout pass, even right after an explicit user resize to 1000pt - the window was effectively stuck. Swapping that one `==` for `>=`/`<=` inequalities (keep the `<=520` cap, position with `leadingAnchor >=`/`trailingAnchor <=`/`centerXAnchor ==` instead of a width tie) removed the trap entirely - verified holding any width the user drags to. This is *why* `HostEditorController`'s max-width-centered column uses inequalities, and it generalizes: any future standalone window with Auto-Layout-capped content needs the same inequality-not-equality shape, or it will silently refuse to stay resized. (4) An `NSScrollView`'s document view belongs width-pinned to `scroll.contentView.widthAnchor` (the clip view), never `scroll.widthAnchor` (the outer view) - caught in code review, not by inspection. With "Show scroll bars: Always" (System Settings, the default with a mouse attached), a non-overlay vertical scroller reserves a real ~15pt track that narrows the clip view without narrowing `scroll`'s own frame; pinning to `scroll.widthAnchor` lets the document view's trailing edge render underneath that track. `HostEditorController`, `FleetController`, and `ReviewController` (the last two fixed in cockpit-native-fixes5) all use `scroll.contentView.widthAnchor`; `SettingsController`'s otherwise-identical scroll setup still has the `scroll.widthAnchor` version and needs the same fix whenever it's next touched. (5) In a horizontal `NSStackView` row (icon + title/subtitle text + a trailing status pill and/or buttons), leaving every subview's compression resistance at its AppKit default (750, all equal) means a long title squeezes *every* subview roughly proportionally under narrow width, not just the title - and since the trailing pill/buttons are themselves small containers with edge-pinned labels, squeezing them below their fitting width can visually read as the badge "wrapping" even though nothing is a wrapping label (cockpit-native-settings-compact, `FleetController`'s PR/task rows). Fix: give the icon and every trailing control `.required` compression resistance (and hugging) so they never shrink, and give the title/subtitle text stack `.defaultLow` compression resistance so it's the one thing that truncates first. Generalizes to any row mixing fixed-size chrome with variable-length text. (6) `NSViewController.dismiss(_:)` is a documented no-op unless the view controller was presented via `presentAsSheet`/`presentAsModalWindow`/`presentAsPopover` (or has a `presentingViewController`) - for a plain top-level window whose `contentViewController` was just assigned directly (`HostEditorController`'s Save/Cancel/Delete, presented by `AppDelegate.presentHostEditor`), `dismiss(self)` silently does nothing. Fixed (cockpit-native-host-form-fixes) by closing the window directly (`view.window?.close()`) instead; verified live via `NSButton.performClick(nil)` on the located button plus a `win.isVisible` before/after check (no Accessibility permission needed - `performClick` runs the exact target/action path a real click does). Any future standalone-window view controller needs the same direct-close pattern, not `dismiss(self)`. (7) A second regular `NSWindow` opened while another app window is full screen docks into that same full-screen Space as a full-width tile by default (macOS's standard behavior for a second standard window) - this is what turned `HostEditorController`'s centered form back into a full-width layout, but only in full-screen mode. Fixed by setting `win.collectionBehavior = [.fullScreenAuxiliary, .moveToActiveSpace]` and `win.level = .floating` on the host editor's cached window in `presentHostEditor`, so it floats over the full-screen Space instead of tiling into it. Verified live via a temporary env-var-gated probe (`window.toggleFullScreen(nil)` then dump `win.frame` vs `screen.frame` - width stayed 640pt against a 1512pt screen, not stretched to match). Any future utility window opened over a possibly-full-screen main window needs the same `collectionBehavior`/`level` pair. (8) `NSVisualEffectView` with `.sidebar` material and `.behindWindow` blending mode - used for a real split-view sidebar, where it blends against the desktop through the window's own edge - renders an incorrect tint when used as a *full-size* destination or standalone window root, since `.behindWindow` blending composites against whatever is behind the *window* (desktop/other apps), not other content inside the same window (cockpit-native-theme-audit-review; same root cause independently hit and fixed for the Hosts sidebar in PR #18's Fix 6, then for the icon rail, `KeysSidebarController`, and `SnippetsController` in this task). Forcing the view's own `.appearance` does not fix it - only removing the vibrancy material does. Any full-size destination or standalone window's root should be a plain `NSView` with `wantsLayer = true` and a `HelmTheme`-derived `layer.backgroundColor`, exactly like `HostsSidebarController`/`FleetController`/`ConsoleController` already do; reserve real `NSVisualEffectView` sidebar material for an actual split-view pane with narrower, non-full-window geometry. (9) A plain `NSView()` used as an `NSScrollView`'s document view is **not flipped** by default, so y=0 is its *bottom*, not its top - while `FleetController`/`ReviewController` pin their `NSStackView` content to the document's *top* anchor (so the header is the visually topmost, highest-y arranged subview), a document shorter than the scroll's viewport (true before their background `gh`/Bitbucket fetch populates the section stacks) rests against the *bottom* of the clip view by default, leaving a blank gap the size of the shortfall sitting above the header - this is the "empty black area above the header for several seconds" bug (cockpit-native-loading-state). Confirmed live with a temporary geometry probe: with a plain `NSView`, the header sat at y=438 in a 668pt-tall viewport with 254pt of content (668-254=414, matching the gap exactly); swapping in `SettingsController`'s existing `FlippedView` (`override var isFlipped: Bool { true }`) pinned the header to y=24 and kept it there from frame 0 through 3s of simulated load. `SettingsController` already used this `FlippedView` + an explicit `scrollToTop()` in `viewWillAppear` (its own earlier Fix 4) - `FleetController`/`ReviewController` were simply built without carrying that pattern forward. Any new `NSScrollView`-backed destination needs the same `FlippedView` document view + `scrollToTop()` pair, or it will silently reproduce this bug the moment its content starts smaller than the viewport (e.g. during an async data load, or a genuinely short list). Follow-up (cockpit-native-fixes5): a captain report of the gap recurring specifically on the *first-ever* Overview visit after a cold launch could not be reproduced via extensive live instrumentation (geometry, `needsLayout`/`needsDisplay` flags, and appearance-transition timing all measured correct at every checked point, both on the first `isHidden`-toggle-triggered `viewWillAppear` and after the async `render()` grows the document height while already visible) - see that task's PR description for the actual probe transcripts. `viewWillAppear` and the end of `render()` in both controllers now force `view.layoutSubtreeIfNeeded()` immediately before `scrollToTop()` regardless, closing the two theoretical gaps the investigation could identify (a first-ever layout pass racing the automatic appearance notification; the scroll position never being re-pinned after the loading-skeleton's short content is replaced by full-height data) even though neither could be proven to be the captain's exact cause.
- **Contrast: `HelmTheme.mutedInk(_:)` is the one "muted/secondary text" token (fixes4 Fix 8).** Alpha-blending `chromeInkHex` at whatever opacity looks right in a dark palette (0.4-0.65 were previously scattered through `FleetController` and the now-removed placeholder stub) can silently drop well below WCAG AA (measured as low as 3.33:1) in the four *light* palettes, since the same alpha lands very differently against a light vs. dark backdrop. `mutedInk` is a measured-safe floor (0.7, worst case ~5.06:1 across all 8 themes' `backgroundHex`/`chromeBackgroundHex`) - route new muted text through it rather than picking an alpha ad hoc. Also: any view that uses `.secondaryLabelColor`/`.tertiaryLabelColor` or other system-semantic colors MUST force its root view's `.appearance` to `.darkAqua`/`.aqua` matching the active Helm theme inside its `ThemeManager.shared.observe` callback (see the `HelmTheme.swift` bullet below) - `FleetController` and `HostEditorController`'s standalone window both skipped this, so their secondary text resolved against the OS's actual light/dark setting instead of the in-app theme, going near-invisible whenever the two disagreed.
