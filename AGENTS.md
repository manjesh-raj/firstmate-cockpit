# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.

## Runtime

- Needs Python 3.11+ (see `pyproject.toml`). The system `python3` on this Mac is 3.9, which cannot evaluate the `str | None` annotations in the pydantic models and fails at import. Build the venv with `python3.12`: `python3.12 -m venv .venv`.
- Dev server: `.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8766`. Native app: `desktop.py` (pywebview); `FM_COCKPIT_NO_WINDOW=1` starts the server only, prints readiness, then exits.

## Auth

- Sign-in is file-based (`backend/auth.py`): a plaintext `~/.firstmate-cockpit/credentials` (path overridable via `FM_CREDENTIALS_FILE`), created with defaults on first run. Sessions are signed with a persistent key using stdlib `hmac` only - deliberately no `itsdangerous`/JWT dep so the py2app bundle stays simple.
- All `/api/*` (except login/logout/auth-status/health) and both websockets are gated by a signed cookie. `/` and `/static/*` stay public so the page can serve the login screen and handle 401s itself.

## Open PRs across the fleet (`/api/open-prs`)

- `backend/openprs.py` walks `$FM_HOME/projects/*`, reads each clone's `origin` remote, and lists every OPEN PR per forge. GitHub uses the operator's authed `gh` CLI; Bitbucket hits the REST API with the cached git credential from `git credential fill`. Result is cached ~60s (`_TTL`); a clone with no remote / no usable credential is skipped, never failing the endpoint.
- Bitbucket gotcha: the cached credential's username (a bare Bitbucket handle like `manjeshp`) is rejected by the REST API when the stored password is an Atlassian API token - the token must be paired with the account **email**. `_bb_candidates()` therefore tries the credential username first, then falls back to `git config --global user.email`, and memoizes whichever works.
- The dashboard merges these with active-work PRs (dedupe by url in `mergedPRs()` in `index.html`); work PRs keep the Merge affordance, forge-only PRs get a Review button that opens the PR on its forge.

## Front-end: the "Helm" UI (`backend/static/index.html`)

- The whole UI is one self-contained file (system fonts, inline SVG, vendored JS, no CDN - keeps the py2app bundle simple). It is the "Helm" instrument-panel redesign: a nav rail, a top bar with a one-click target switcher + theme menu, and four views - **Fleet** (decision-first dashboard: answer banner that goes calm/loud, Needs-you, In flight, Ready to merge, quiet readouts incl. the watcher-health signal), **Console**, **Review** (open PRs grouped by forge), **Settings**. App view/tab state lives on `#app` (`dataset.view` / `dataset.tab`).
- **Themes are OKLCH tokens with a hard WCAG-AA gate.** A curated set of dark + light themes (`:root[data-theme="..."]` blocks). `scripts/verify-contrast.mjs` is the **single source of truth**: `node scripts/verify-contrast.mjs verify` converts OKLCH -> sRGB -> WCAG luminance and fails if any key text/UI pair (incl. pill-text-on-tint and icon-on-solid-amber) is < 4.5:1; `... css` re-emits the exact token blocks pasted into `index.html`. Change a theme colour there, re-run the gate, re-emit. AA is an acceptance gate, not a nicety.
- The "needs you" **amber** is built entirely from each theme's own `--need` / `--need-ink` tokens (not one fixed hue), so the attention banner harmonises with every theme while still reading loud. Legacy `localStorage['fm-theme']` ids migrate to the default (`helm-dark`).

## Console: Terminal + Shell (xterm.js, one view, two tabs)

- Terminal and Shell are merged into one **Console** view with two tabs: **Live terminal** (`⌘2`) and **Shell** (`⌘3`). Both are real xterm.js; the fit/focus/reconnect guards key off `termVisible()` / `shellVisible()` (view===console && the active tab). All existing wiring is preserved: search, A−/A+ zoom, independent terminal palette, copy, jump-to-bottom, auto-reconnect, and the captain composer (`/api/send`) on the live tab.
- The live terminal attaches to a per-connection *grouped* tmux mirror (`backend/terminal.py`). The group name carries a per-connection suffix (`cockpit_<session>_<pid>_<hex>`) so two cockpit instances don't fight over one shared mirror and kill each other's attach (that showed up as a dead `[exited]` frame). When the inner tmux client exits, the bridge closes the socket so the frontend auto-reconnects.
- The Shell tab is a genuine `pty.fork()` login shell (`backend/shell.py`, `/ws/shell`, same auth gate as `/ws/terminal`), so lines that scroll off the top land in xterm's scrollback. The scrollback win is **primary-screen only**; the shell's wheel handler is conditional (`initShell`): native xterm scroll while `shTerm.buffer.active.type==='normal'`, PageUp/PageDown only when `'alternate'`. The mirror tab hijacks the wheel to PageUp/PageDown unconditionally (it is always alt-screen).
- Light-terminal readability (`matchAppTheme`/`applyTermTheme`): the first mate emits much output as **truecolor (24-bit)**, which the ANSI palette can't remap - so xterm's `minimumContrastRatio` is raised to 4.5 (`contrastFloorFor()`) whenever the terminal bg is light by WCAG luminance, darkening *any* foreground to meet contrast; dark terminals keep it at 1 (off). App tokens are OKLCH, but xterm needs concrete colours, so `cssColorToHex()` converts the current theme's `--term-bg`/`--ink`/`--accent`/`--muted` to hex before handing them to xterm.
- **Vendored xterm** (`backend/static/vendor/`, all self-contained UMD, no CDN): scoped `@xterm/xterm@5.5.0` (global `Terminal`), `@xterm/addon-fit@0.10.0` (`FitAddon.FitAddon`), and `@xterm/addon-webgl@0.18.0` (`WebglAddon.WebglAddon`). WebGL is loaded via `loadWebgl()` after `term.open()` with an `onContextLoss(() => dispose())` fallback so a lost WKWebView GL context degrades to the DOM renderer. Both terminals set `smoothScrollDuration:110` for native-feel scrolling. If you bump the core, re-match the addon versions (byte-compare against `npm pack`).
- Image/screenshot paste-into-agent needs no cockpit code: xterm forwards a browser paste as a **bracketed paste** (`ESC[200~…ESC[201~`) over the socket to the PTY, and the agent reads the shared macOS system clipboard for the image. Both tabs share the `term.onData -> ws.send` wiring, so paste works identically in either - do not touch that wiring.

## Native app (`native/`, Swift + SwiftTerm)

- A separate, growing native macOS surface that will eventually replace the web terminal. **It does not touch `backend/` or `desktop.py`** - keep them independent. Build with `swift build` / run with `swift run` from `native/` (Command Line Tools only, **no Xcode / `xcodebuild`**). First build is ~90s. Full run + captain-validation steps live in `native/README.md`; the authoritative design + verified API shapes are in `data/cockpit-native-design-scout/report.md` (sections 3, 4.3, 5, 6, 7, 9).
- **SwiftTerm is vendored, not a remote SPM dependency** (`native/Vendor/SwiftTerm/`, pinned to upstream 1.15.0 / commit `dd2fb8ac...`; `Package.resolved` no longer exists, since there are no remote dependencies left). This is a deliberate patch, not a stylistic choice: SGR-2 (dim/faint) text rendering (`NSColor.dimmedColor(towards:)` in `Mac/MacExtensions.swift`, mirrored in `iOS/iOSExtensions.swift`) blended a flat 50% toward the background regardless of whether that background was dark or light - fine on dark themes (~4.9:1 contrast) but collapsing to ~2.9:1, nearly invisible, on light ones - and none of `dimmedColor`, `getAttributes`, `buildAttributedString`, or `mapColor` are `open` (nor is `TerminalView.draw(_:)`), so there is no override point from outside the module. The patch (new file `Dimming.swift`) targets a fixed 4.5:1 WCAG contrast ratio against the background via bisection, capped at the original 50% so dark themes render unchanged. See `native/Vendor/SwiftTerm/README.md` for the full writeup and how to re-apply the patch if SwiftTerm is ever upgraded.
- **Second SwiftTerm patch: truecolor de-emphasised text (cockpit-native-fixes5).** The `dimmedColor` patch above only fires for the SGR-2 "faint" attribute - some tools de-emphasise text via a literal 24-bit truecolor foreground instead (`ESC[38;2;r;g;bm`), which carries no theme awareness at all since the child process chose concrete RGB bytes with no idea what background they'd land on. Confirmed live via `tmux capture-pane -e` on a real firstmate session: Claude Code renders its own status lines ("Searched for N files...") as `ESC[38;2;153;153;153m`, not SGR-2 dim - ~6.7:1 contrast on a dark theme (fine) but ~2.55:1 on light (illegible), and `getAttributes`'s `.dim` branch never touches it. `getAttributes` (`Apple/AppleTerminalView.swift`) now also checks `attribute.fg` for the `.trueColor` case and calls the new `NSColor.legibleColor(against:)`/`UIColor.legibleColor(against:)` (`Mac/MacExtensions.swift` / `iOS/iOSExtensions.swift`, backed by `Dimming.contrastFixBlendFraction`), which remaps *any* truecolor foreground that doesn't already meet the contrast floor - self-gating (no-op once contrast is sufficient) and hue-preserving (blends toward whichever of black/white the color can reach the most contrast against, not simply "toward its own background" like the dim patch - that direction has to be chosen by evaluating both endpoints, since a foreground already close to one extreme has almost no headroom left in that direction). See `native/Vendor/SwiftTerm/README.md`'s "Second patch" section.

- **SSH keychain (Phase 2, `data/cockpit-ssh-manager-research/report.md` A1, C3, D Phase 2; Keychain model corrected in cockpit-native-fixes3).** `SSHKey.swift` is non-secret metadata only (label, type, derived public key, fingerprint, certificate), persisted by `SSHKeyStore` to `keys.json` (override `FM_KEYS_FILE`) exactly like `HostStore`. Private key bytes and passphrase live **only** in the macOS Keychain (`KeychainKeyStore.swift`: `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete`), stored with plain `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (never iCloud-synced) - **not** a `SecAccessControl` ACL. That's a deliberate correction, not the original design: on a CLT-only, ad-hoc-signed build (`TeamIdentifier=not set`), `SecItemAdd` with *any* `kSecAttrAccessControl` fails `errSecMissingEntitlement`, confirmed with a standalone probe outside the app - see `KeychainKeyStore.swift`'s file header for the full writeup, including why a `keychain-access-groups` entitlement isn't a fix either (ad-hoc signing it gets the process killed outright, no provisioning profile). The Touch ID / passcode gate is therefore enforced in-app (`KeychainKeyStore.authenticate(context:)` calling `LAContext.evaluatePolicy` before the read), not by the OS ACL - revisit once the app has a real Team ID (Phase 4 packaging). Generation and PEM/OpenSSH import both shell out to `/usr/bin/ssh-keygen` (`SSHKeyGenerator.swift`) rather than reimplementing the OpenSSH key format or its passphrase KDF - `.ppk` files are detected and rejected with a conversion hint, not parsed. `SSHKeyStore.addNew(_:privateKeyData:passphrase:)` is the one path that writes a brand-new key (Keychain first, then metadata) - both the Keys screen and the host editor's inline "+ New Key…" popup entry (`HostEditorController.presentNewKeySheet`, still a sheet - now on the host editor's own window rather than the sidebar's) go through it, so a new key can be created without leaving the host form. At connect time `SSHKeyMaterializer.materialize` does the one Keychain read (the Touch ID prompt) and writes a private `0600` temp file for `ssh -i`; `ConsoleController.connectSSH`/`cleanupSSHKeyTempFile` own its lifecycle (fresh file per tab start/reconnect, deleted on close/exit/quit). The "SSH Keys" browser (`KeysSidebarController.swift` + `KeyEditorController.swift`) is a separate window (Keys menu, `⌘⇧K`/`⌘⇧N`), not a rail destination. Known caveat: an unsigned `swift build`/`swift run` binary has no stable code-signing identity, so Keychain access can prompt again (or rarely fail to re-read) across rebuilds - resolves once the app is signed (Phase 4).

- **Nine confirmed AppKit gotchas worth knowing before touching tab chips, a scroll view, the host editor form, a dense row layout, or any full-size destination/window root.** (1) `TabChipView.beginRename()` (fixes4) used to call `window.makeFirstResponder(label)` *and then* `label.selectText(nil)` - `selectText(nil)` alone already makes an editable field first responder and starts editing, so the redundant prior `makeFirstResponder` call makes AppKit think a session is already active and needs ending before `selectText` starts its own. That fires a spurious `controlTextDidEndEditing` with the *pre-edit* text right there, permanently flipping the "is renaming" flag false before the user types a single character - the rename UI looks like it's working, but the real commit on Return later hits a now-stale guard and is silently dropped. Root-caused via `Thread.callStackSymbols` inside the delegate callback, not by reading the code. Never call both; `selectText(nil)` is sufficient on its own. (2) `NSGridView` column widths: setting an explicit pixel width on one column (e.g. the field column) while leaving the other unconstrained does NOT make the constrained column absorb extra space on window resize - the *unconstrained* column absorbs 100% of any extra width instead, since nothing else defines where it should stop. That's what caused the "Add Host" form's labels to drift into a growing empty gap as the window widened. Fix: give the column that should *stay* narrow (labels) the explicit width, leave the column that should *fill* (fields) unconstrained, and pin the `NSGridView`'s own width to its container (`widthAnchor.constraint(equalTo: stack.widthAnchor)`) so the fill column has a definite total to fill. (3) A standalone `NSWindow` with `contentViewController` assigned (as opposed to embedded in the shared app-shell body) keeps re-deriving its own frame from its content's Auto Layout fitting size for as long as that content contains a **required equality** chain with no independent lower bound (cockpit-native-host-pages) - not just once at open. Confirmed live (`FM_DEBUG_HOSTEDITOR`-style probe: `setFrame`/`display:true` right after, then read `win.frame` again after a runloop tick): capping-and-centering the host editor's form column with a required `stack.widthAnchor == content.widthAnchor - 48` (paired with a `<=520` cap) made AppKit snap the *whole window* back to 568pt (the one width where that equality has zero slack) within one layout pass, even right after an explicit user resize to 1000pt - the window was effectively stuck. Swapping that one `==` for `>=`/`<=` inequalities (keep the `<=520` cap, position with `leadingAnchor >=`/`trailingAnchor <=`/`centerXAnchor ==` instead of a width tie) removed the trap entirely - verified holding any width the user drags to. This is *why* `HostEditorController`'s max-width-centered column uses inequalities, and it generalizes: any future standalone window with Auto-Layout-capped content needs the same inequality-not-equality shape, or it will silently refuse to stay resized. (4) An `NSScrollView`'s document view belongs width-pinned to `scroll.contentView.widthAnchor` (the clip view), never `scroll.widthAnchor` (the outer view) - caught in code review, not by inspection. With "Show scroll bars: Always" (System Settings, the default with a mouse attached), a non-overlay vertical scroller reserves a real ~15pt track that narrows the clip view without narrowing `scroll`'s own frame; pinning to `scroll.widthAnchor` lets the document view's trailing edge render underneath that track. `HostEditorController`, `FleetController`, and `ReviewController` (the last two fixed in cockpit-native-fixes5) all use `scroll.contentView.widthAnchor`; `SettingsController`'s otherwise-identical scroll setup still has the `scroll.widthAnchor` version and needs the same fix whenever it's next touched. (5) In a horizontal `NSStackView` row (icon + title/subtitle text + a trailing status pill and/or buttons), leaving every subview's compression resistance at its AppKit default (750, all equal) means a long title squeezes *every* subview roughly proportionally under narrow width, not just the title - and since the trailing pill/buttons are themselves small containers with edge-pinned labels, squeezing them below their fitting width can visually read as the badge "wrapping" even though nothing is a wrapping label (cockpit-native-settings-compact, `FleetController`'s PR/task rows). Fix: give the icon and every trailing control `.required` compression resistance (and hugging) so they never shrink, and give the title/subtitle text stack `.defaultLow` compression resistance so it's the one thing that truncates first. Generalizes to any row mixing fixed-size chrome with variable-length text. (6) `NSViewController.dismiss(_:)` is a documented no-op unless the view controller was presented via `presentAsSheet`/`presentAsModalWindow`/`presentAsPopover` (or has a `presentingViewController`) - for a plain top-level window whose `contentViewController` was just assigned directly (`HostEditorController`'s Save/Cancel/Delete, presented by `AppDelegate.presentHostEditor`), `dismiss(self)` silently does nothing. Fixed (cockpit-native-host-form-fixes) by closing the window directly (`view.window?.close()`) instead; verified live via `NSButton.performClick(nil)` on the located button plus a `win.isVisible` before/after check (no Accessibility permission needed - `performClick` runs the exact target/action path a real click does). Any future standalone-window view controller needs the same direct-close pattern, not `dismiss(self)`. (7) A second regular `NSWindow` opened while another app window is full screen docks into that same full-screen Space as a full-width tile by default (macOS's standard behavior for a second standard window) - this is what turned `HostEditorController`'s centered form back into a full-width layout, but only in full-screen mode. Fixed by setting `win.collectionBehavior = [.fullScreenAuxiliary, .moveToActiveSpace]` and `win.level = .floating` on the host editor's cached window in `presentHostEditor`, so it floats over the full-screen Space instead of tiling into it. Verified live via a temporary env-var-gated probe (`window.toggleFullScreen(nil)` then dump `win.frame` vs `screen.frame` - width stayed 640pt against a 1512pt screen, not stretched to match). Any future utility window opened over a possibly-full-screen main window needs the same `collectionBehavior`/`level` pair. (8) `NSVisualEffectView` with `.sidebar` material and `.behindWindow` blending mode - used for a real split-view sidebar, where it blends against the desktop through the window's own edge - renders an incorrect tint when used as a *full-size* destination or standalone window root, since `.behindWindow` blending composites against whatever is behind the *window* (desktop/other apps), not other content inside the same window (cockpit-native-theme-audit-review; same root cause independently hit and fixed for the Hosts sidebar in PR #18's Fix 6, then for the icon rail, `KeysSidebarController`, and `SnippetsController` in this task). Forcing the view's own `.appearance` does not fix it - only removing the vibrancy material does. Any full-size destination or standalone window's root should be a plain `NSView` with `wantsLayer = true` and a `HelmTheme`-derived `layer.backgroundColor`, exactly like `HostsSidebarController`/`FleetController`/`ConsoleController` already do; reserve real `NSVisualEffectView` sidebar material for an actual split-view pane with narrower, non-full-window geometry. (9) A plain `NSView()` used as an `NSScrollView`'s document view is **not flipped** by default, so y=0 is its *bottom*, not its top - while `FleetController`/`ReviewController` pin their `NSStackView` content to the document's *top* anchor (so the header is the visually topmost, highest-y arranged subview), a document shorter than the scroll's viewport (true before their background `gh`/Bitbucket fetch populates the section stacks) rests against the *bottom* of the clip view by default, leaving a blank gap the size of the shortfall sitting above the header - this is the "empty black area above the header for several seconds" bug (cockpit-native-loading-state). Confirmed live with a temporary geometry probe: with a plain `NSView`, the header sat at y=438 in a 668pt-tall viewport with 254pt of content (668-254=414, matching the gap exactly); swapping in `SettingsController`'s existing `FlippedView` (`override var isFlipped: Bool { true }`) pinned the header to y=24 and kept it there from frame 0 through 3s of simulated load. `SettingsController` already used this `FlippedView` + an explicit `scrollToTop()` in `viewWillAppear` (its own earlier Fix 4) - `FleetController`/`ReviewController` were simply built without carrying that pattern forward. Any new `NSScrollView`-backed destination needs the same `FlippedView` document view + `scrollToTop()` pair, or it will silently reproduce this bug the moment its content starts smaller than the viewport (e.g. during an async data load, or a genuinely short list). Follow-up (cockpit-native-fixes5): a captain report of the gap recurring specifically on the *first-ever* Overview visit after a cold launch could not be reproduced via extensive live instrumentation (geometry, `needsLayout`/`needsDisplay` flags, and appearance-transition timing all measured correct at every checked point, both on the first `isHidden`-toggle-triggered `viewWillAppear` and after the async `render()` grows the document height while already visible) - see that task's PR description for the actual probe transcripts. `viewWillAppear` and the end of `render()` in both controllers now force `view.layoutSubtreeIfNeeded()` immediately before `scrollToTop()` regardless, closing the two theoretical gaps the investigation could identify (a first-ever layout pass racing the automatic appearance notification; the scroll position never being re-pinned after the loading-skeleton's short content is replaced by full-height data) even though neither could be proven to be the captain's exact cause.
- **Contrast: `HelmTheme.mutedInk(_:)` is the one "muted/secondary text" token (fixes4 Fix 8).** Alpha-blending `chromeInkHex` at whatever opacity looks right in a dark palette (0.4-0.65 were previously scattered through `FleetController` and the now-removed placeholder stub) can silently drop well below WCAG AA (measured as low as 3.33:1) in the four *light* palettes, since the same alpha lands very differently against a light vs. dark backdrop. `mutedInk` is a measured-safe floor (0.7, worst case ~5.06:1 across all 8 themes' `backgroundHex`/`chromeBackgroundHex`) - route new muted text through it rather than picking an alpha ad hoc. Also: any view that uses `.secondaryLabelColor`/`.tertiaryLabelColor` or other system-semantic colors MUST force its root view's `.appearance` to `.darkAqua`/`.aqua` matching the active Helm theme inside its `ThemeManager.shared.observe` callback (see the `HelmTheme.swift` bullet below) - `FleetController` and `HostEditorController`'s standalone window both skipped this, so their secondary text resolved against the OS's actual light/dark setting instead of the in-app theme, going near-invisible whenever the two disagreed.
- **Toast.swift is the one save-confirmation pattern (fixes4 Fix 5).** `Toast.show(in:message:)` drops a small auto-dismissing pill at the top of any view. Host saves show it on `AppShellController.view` (not the host editor's own view, since that window closes immediately on Save); key saves show it directly on `KeysSidebarController.view` (that window stays open, sheet-presented editor closes on top of it).
- **`HelmTheme.swift` holds all 8 Helm palettes as concrete sRGB hex** (Helm Dark/Light hand-pinned; Midnight/Graphite/Nocturne/Paper/Frost/Linen derived at load time by `HelmTheme`'s own OKLCH->sRGB conversion, mirroring `scripts/verify-contrast.mjs`'s math, from the same OKLCH tokens as `backend/static/index.html`'s `:root[data-theme=...]` blocks - the ANSI reds/greens/yellows are shared with `dark`/`light` since those tokens barely change per theme; only accent-linked ANSI slots and the chrome/cursor colours are re-derived). If a token changes in the web CSS, update the matching tuple in `HelmTheme`'s `derived(...)` calls. **`ThemeManager.swift` is the single source of truth for which of the 8 is active**, persisted by `HelmTheme.id` (migrates a pre-nav-redesign "fm.themeMode" dark/light pref once) - `ConsoleController` and every other theme-aware window/view (`HostsSidebarController`, `KeysSidebarController`, `SnippetsController`, `IconRailController`, `TopBarController`, `SettingsController`, `ReviewController`, `FleetController`, and every sheet editor) call `ThemeManager.shared.observe { ... }` rather than tracking their own copy - see the checklist at the top of `ThemeManager.swift` and `NSWindow.followHelmTheme()` (for a window's own title-bar chrome, which has no view to hook) for the full convention this task established after finding and fixing the same class of bug three separate times. `observe` returns a discardable `ThemeObservation` token (cockpit-native-host-pages) - every one of those call sites is an app-lifetime singleton and can ignore it, but `ConsoleController` keeps its token and passes it to `ThemeManager.shared.unobserve` inside `shutdown()`, since Fix 1 made it the first view controller in this app that can be deallocated mid-session (a deleted host's dedicated page) - skipping that would leak a dead closure into `ThemeManager.observers` on every delete. A window/view using `NSVisualEffectView` (or plain semantic system colors) needs its `appearance` forced to `.darkAqua`/`.aqua` in that observer for its colors to resolve against the Helm mode instead of macOS's own light/dark setting - `SettingsController` needed this added when it moved from its own floating window into the shared, always-themed body area (nav-redesign task). `ThemeMenu.swift` builds the shared DARK/LIGHT-grouped, swatch + checkmark `NSMenu` used by both the topbar's theme button and Settings' Appearance row.
- **`AppSettings.swift` + `SettingsController.swift` (⌘, / App menu > Settings…, or the rail's gear icon) are the native Settings panel** - three cards, matching the web app's Connection/Appearance/Terminal visual weight (icon + title headers, generous spacing, no Sign-in card - native has no login): **Connection** (mirror-target field + a live `TmuxMirror.listSessions()` session-picker of selectable cards, plus the working-directory chooser); **Appearance** (the 8 `HelmTheme.allThemes` as a DARK/LIGHT-grouped wrapping grid of preview cards - swatch bars + name + checkmark - built by `SettingsController.rebuildAppearanceGrid`, the same source of truth `ThemeMenu` uses for the topbar picker); **Terminal** (font-size presets 12/13/14/16 via `ConsoleController.stepFontSize`, plus three `NSSwitch` toggles: "Reconnect automatically" - `AppSettings.autoReconnect`, read by `ConsoleController.processTerminated` to actually re-run a dropped tab's launch after a short delay instead of only showing the ⌘R hint; "Bell & notifications" - `AppSettings.notifyOnNeedsDecision`, driving `FleetNotifier`'s background poll of `FleetDataSource.parseTasks()` to post a real macOS notification the first time a task newly needs the captain; and session-logging-by-default, moved here from the old General section). `FM_SHELL_CWD`/`FM_MIRROR_TARGET`/`FM_LOG_SESSIONS_DEFAULT` env vars still win when set, `AppSettings` (backed by `UserDefaults`) is the fallback.
- **Find (Fix 4, cockpit-native-ui-fixes2).** The topbar Search pill / its ⌘K calls `AppShellController.activateConsoleFind()`, which brings Console forward and calls `ConsoleController.showFind()` - the exact same in-terminal find the console toolbar's own magnifying-glass icon triggers (SwiftTerm's native find bar on the active tab). There is one search behavior in the app, not two; it has nothing to do with Hosts.
- **Verifying native UI bugs without a real screenshot.** This machine has a real console session, but the agent's shell process (`claude` under WezTerm) has neither Screen Recording nor Accessibility permission granted, and there is no way to grant either non-interactively (`screencapture`/`osascript "System Events"` both fail, TCC.db is SIP-protected even to root, no passwordless sudo). The effective substitute that actually caught real bugs (fixes4): add temporary, env-var-gated debug code straight into the controller under test - print live `NSView.frame` geometry after a real layout pass, or a `Thread.callStackSymbols` dump inside a suspect delegate callback - `swift build && FM_DEBUG_X=1 .build/debug/FirstmateCockpit`, read the printed numbers/stack, then revert the instrumentation before committing. This is real evidence from AppKit's actual layout/event engine, not a screenshot, but it is not guesswork either - say so explicitly in any PR that relies on it instead of claiming a visual check that didn't happen.
- **Two app bundles live under `dist/` (gitignored) and are easy to confuse.** `dist/Firstmate.app` is the old web/WKWebView app (`backend/` + `desktop.py`, built by the root `build_app.sh` via py2app). `dist/New-Firstmate.app` is this native Swift cockpit, built by `native/build_native_app.sh` (plain `swift build -c release` + manual bundle assembly, no py2app, unsigned, bundle ID `com.firstmate.cockpit.native`). Check the name before opening either.
- **"Firstmate Latest Updates" (`UpdatesController.swift` + `UpdatesData.swift`, cockpit-native-updates-page).** A `.updates` rail destination (person-silhouette icon, pinned directly above Settings the same way Settings is pinned above the avatar - see `IconRailController.loadView`'s bottom-anchored chain) listing every tool in the captain's ecosystem (npm-global `*-axi` packages, Homebrew `gh`/`tmux`/the `claude-code` cask, herdr, no-mistakes, and firstmate's own upstream sync), each checked automatically on page load and updatable with one explicit click - Settings-styled cards/rows, per-row spinner + expandable command-output log, a `Toast` + `UNUserNotificationCenter` notification on success. Two non-obvious things any future change to this page should know: (1) `UNUserNotificationCenter.current()` throws an uncaught `NSException` ("bundleProxyForCurrentProcess is nil") when the running process has no real `Info.plist`/bundle identifier - true for the README's own documented `swift run`/bare `.build/debug/FirstmateCockpit` dev workflow - so `UpdatesController.notify` guards on `Bundle.main.bundleIdentifier != nil` first; the packaged app (a real bundle) is unaffected either way. (2) `no-mistakes --version`'s own output ("no-mistakes version v1.37.0 …") contains a decoy "v" inside the word "version" before the real "v1.37.0" token - parse whitespace-separated tokens shaped `v<digit>...`, not the first bare "v" in the string (caught live: the naive version crashed every check silently). no-mistakes has no `--check` flag; its outdated-version banner only prints on stderr from a real subcommand's `--help` (itself a safe no-op), which is what's parsed instead. herdr similarly has no "check without updating" flag - latest-available is read from Homebrew (herdr happens to be homebrew-core tapped here) while the actual Update action still runs herdr's own `herdr update`, never `brew upgrade herdr`. Firstmate's own row shells out to `bin/fm-sync-upstream.sh` (a firstmate-repo file, out of scope for this cockpit repo to commit - see the PR that introduced this page for its exact content) and gracefully reports `.notInstalled` if that script isn't present yet, rather than failing.
