## Runtime

The native Swift cockpit (`native/`) is the only app in this repo. The old Python/FastAPI backend, its WKWebView shell (`desktop.py`), and its py2app packaging (`build_app.sh`, `setup.py`, `pyproject.toml`) were removed once the native app became feature-complete - see `native/README.md` for build/run instructions.

## Native app (`native/`, Swift + SwiftTerm)

- The sole cockpit surface. Build with `swift build` / run with `swift run` from `native/` (Command Line Tools only, **no Xcode / `xcodebuild`**). First build is ~90s. Full run + captain-validation steps live in `native/README.md`; the authoritative design + verified API shapes are in `data/cockpit-native-design-scout/report.md` (sections 3, 4.3, 5, 6, 7, 9).
- **SwiftTerm is vendored, not a remote SPM dependency** (`native/Vendor/SwiftTerm/`, pinned to upstream 1.15.0 / commit `dd2fb8ac...`; `Package.resolved` no longer exists, since there are no remote dependencies left). This is a deliberate patch, not a stylistic choice: SGR-2 (dim/faint) text rendering (`NSColor.dimmedColor(towards:)` in `Mac/MacExtensions.swift`, mirrored in `iOS/iOSExtensions.swift`) blended a flat 50% toward the background regardless of whether that background was dark or light - fine on dark themes (~4.9:1 contrast) but collapsing to ~2.9:1, nearly invisible, on light ones - and none of `dimmedColor`, `getAttributes`, `buildAttributedString`, or `mapColor` are `open` (nor is `TerminalView.draw(_:)`), so there is no override point from outside the module. The patch (new file `Dimming.swift`) targets a fixed 4.5:1 WCAG contrast ratio against the background via bisection, capped at the original 50% so dark themes render unchanged. See `native/Vendor/SwiftTerm/README.md` for the full writeup and how to re-apply the patch if SwiftTerm is ever upgraded.
- **Second SwiftTerm patch: truecolor de-emphasised text (cockpit-native-fixes5).** The `dimmedColor` patch above only fires for the SGR-2 "faint" attribute - some tools de-emphasise text via a literal 24-bit truecolor foreground instead (`ESC[38;2;r;g;bm`), which carries no theme awareness at all since the child process chose concrete RGB bytes with no idea what background they'd land on. Confirmed live via `tmux capture-pane -e` on a real firstmate session: Claude Code renders its own status lines ("Searched for N files...") as `ESC[38;2;153;153;153m`, not SGR-2 dim - ~6.7:1 contrast on a dark theme (fine) but ~2.55:1 on light (illegible), and `getAttributes`'s `.dim` branch never touches it. `getAttributes` (`Apple/AppleTerminalView.swift`) now also checks `attribute.fg` for the `.trueColor` case and calls the new `NSColor.legibleColor(against:)`/`UIColor.legibleColor(against:)` (`Mac/MacExtensions.swift` / `iOS/iOSExtensions.swift`, backed by `Dimming.contrastFixBlendFraction`), which remaps *any* truecolor foreground that doesn't already meet the contrast floor - self-gating (no-op once contrast is sufficient) and hue-preserving (blends toward whichever of black/white the color can reach the most contrast against, not simply "toward its own background" like the dim patch - that direction has to be chosen by evaluating both endpoints, since a foreground already close to one extreme has almost no headroom left in that direction). See `native/Vendor/SwiftTerm/README.md`'s "Second patch" section.
- **The console** (`main.swift` -> `ConsoleController`) hosts a **dynamic tab collection**, not a fixed two-tab enum. Tabs are `[TabModel]` (`TabModel.swift`), each owning a `CockpitTerminalView` + a `TabLaunch` (re)start recipe, rendered as `TabChipView` chips in a growing tab bar. Later phases add the dashboard + embedded backend (P3) and packaging/signing (P4); the console stays backend-free.

- **SSH keychain (Phase 2, `data/cockpit-ssh-manager-research/report.md` A1, C3, D Phase 2; Keychain model corrected in cockpit-native-fixes3).** `SSHKey.swift` is non-secret metadata only (label, type, derived public key, fingerprint, certificate), persisted by `SSHKeyStore` to `keys.json` (override `FM_KEYS_FILE`) exactly like `HostStore`. Private key bytes and passphrase live **only** in the macOS Keychain (`KeychainKeyStore.swift`: `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete`), stored with plain `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (never iCloud-synced) - **not** a `SecAccessControl` ACL. That's a deliberate correction, not the original design: on a CLT-only, ad-hoc-signed build (`TeamIdentifier=not set`), `SecItemAdd` with *any* `kSecAttrAccessControl` fails `errSecMissingEntitlement`, confirmed with a standalone probe outside the app - see `KeychainKeyStore.swift`'s file header for the full writeup, including why a `keychain-access-groups` entitlement isn't a fix either (ad-hoc signing it gets the process killed outright, no provisioning profile). The Touch ID / passcode gate is therefore enforced in-app (`KeychainKeyStore.authenticate(context:)` calling `LAContext.evaluatePolicy` before the read), not by the OS ACL - revisit once the app has a real Team ID (Phase 4 packaging). Generation and PEM/OpenSSH import both shell out to `/usr/bin/ssh-keygen` (`SSHKeyGenerator.swift`) rather than reimplementing the OpenSSH key format or its passphrase KDF - `.ppk` files are detected and rejected with a conversion hint, not parsed. `SSHKeyStore.addNew(_:privateKeyData:passphrase:)` is the one path that writes a brand-new key (Keychain first, then metadata) - both the Keys screen and the host editor's inline "+ New Key…" popup entry (`HostEditorController.presentNewKeySheet`, still a sheet - now on the host editor's own window rather than the sidebar's) go through it, so a new key can be created without leaving the host form. At connect time `SSHKeyMaterializer.materialize` does the one Keychain read (the Touch ID prompt) and writes a private `0600` temp file for `ssh -i`; `ConsoleController.connectSSH`/`cleanupSSHKeyTempFile` own its lifecycle (fresh file per tab start/reconnect, deleted on close/exit/quit). The "SSH Keys" browser (`KeysSidebarController.swift` + `KeyEditorController.swift`) is a separate window (Keys menu, `⌘⇧K`/`⌘⇧N`), not a rail destination, and its footer/context-menu Delete action (`SSHKeyStore.delete(id:)`) removes both the metadata and the Keychain items - see `KeychainKeyStore.delete(id:)`. A `swift build`/`swift run` binary has no stable code-signing identity, so Keychain access can prompt again (or rarely fail to re-read) across rebuilds; `native/build_native_app.sh` now codesigns the assembled `.app` with a fixed local identity to keep that identity stable across rebuilds (see the `build_native_app.sh` bullet below and its "Local signing setup" section in `native/README.md`) - not a full Phase 4 Developer ID/notarization setup, just a per-machine local dev cert.

- **Ten confirmed AppKit gotchas worth knowing before touching tab chips, a scroll view, the host editor form, a dense row layout, or any full-size destination/window root.** (10) A horizontal `NSStackView` left at its default `.gravityAreas` distribution (never set explicitly) does not honor arranged-subviews' hugging/compression-resistance priorities to absorb slack width at all - those priorities only matter under `.fill`/`.fillProportionally`/`.fillEqually`. Under `.gravityAreas`, all views added via the plain `views:` initializer or `addArrangedSubview` land in the *center* gravity area and get laid out at their natural size with no defined "who grows" rule, so leftover width is resolved by Auto Layout's own tie-breaking - which can drift between runs/rows depending on transient sibling content (a spinner swapped for a button, a longer status string) even with no code change. This is what caused the Updates page's per-row disclosure chevron (`UpdatesController.buildRow`'s `topRow`) to sit flush against the trailing edge for some rows and stop short with a stray gap for others, inconsistently, after expanding a row's log. There's a second, compounding trap: even under `.fill`, an `NSStackView` container's *own* horizontal hugging priority (not its children's) defaults lower than any priority you set on its arranged-subview children - so a `trailingStack` of `.required`-hugging buttons/pills can still itself get chosen to absorb the row's slack instead of the intended flexible text label, unless you also set `.required` hugging/compression-resistance on the container view itself. Fix needs both: set `topRow.distribution = .fill` AND give every non-flexible arranged subview (including any nested `NSStackView` container, not just its children) `.required` hugging/compression resistance, leaving only the one view meant to flex (the title/detail text stack) at `.defaultLow`. Confirmed live via a temporary `FM_DEBUG_CHEVRON`-style env-gated probe (`performClick(nil)` on the disclosure button + `ThemeManager.shared.setTheme` cycling, dumping `NSView.frame` for the chevron/trailing-stack/text-stack after each) - reverted before commit, per the "Verifying native UI bugs" convention below. Same root cause hit a third time (cockpit-bootstrap-row-width-parity): `BootstrapController.buildStepRow`'s `row` (a horizontal `[leftColumn, bodyStack]` stack wrapping each stepper step's content box) also left `.gravityAreas` distribution unset, so `bodyStack` - and therefore the `stepContentBox` nested inside it - stayed shrunk to its content's natural width even though the step's own outer card correctly filled the page (the card's `background` *was* already width-tied to the page via an external `widthAnchor.constraint(equalTo: stack.widthAnchor)`, so the empty gap looked like a "card too narrow" bug but was actually this same nested-row distribution gap one level in). Confirmed live via an `FM_DEBUG_BOOTSTRAP_WIDTH`-style probe dumping `stepContentBox` frame widths before/after the fix (169-467pt narrow -> 1044pt full-width, tracking window resize correctly afterward) - fixed by adding `row.distribution = .fill` plus `.required` hugging/compression resistance on `leftColumn` and `.defaultLow` on `bodyStack`, the same shape as the Updates-page fix above. (1) `TabChipView.beginRename()` (fixes4) used to call `window.makeFirstResponder(label)` *and then* `label.selectText(nil)` - `selectText(nil)` alone already makes an editable field first responder and starts editing, so the redundant prior `makeFirstResponder` call makes AppKit think a session is already active and needs ending before `selectText` starts its own. That fires a spurious `controlTextDidEndEditing` with the *pre-edit* text right there, permanently flipping the "is renaming" flag false before the user types a single character - the rename UI looks like it's working, but the real commit on Return later hits a now-stale guard and is silently dropped. Root-caused via `Thread.callStackSymbols` inside the delegate callback, not by reading the code. Never call both; `selectText(nil)` is sufficient on its own. (2) `NSGridView` column widths: setting an explicit pixel width on one column (e.g. the field column) while leaving the other unconstrained does NOT make the constrained column absorb extra space on window resize - the *unconstrained* column absorbs 100% of any extra width instead, since nothing else defines where it should stop. That's what caused the "Add Host" form's labels to drift into a growing empty gap as the window widened. Fix: give the column that should *stay* narrow (labels) the explicit width, leave the column that should *fill* (fields) unconstrained, and pin the `NSGridView`'s own width to its container (`widthAnchor.constraint(equalTo: stack.widthAnchor)`) so the fill column has a definite total to fill. (3) A standalone `NSWindow` with `contentViewController` assigned (as opposed to embedded in the shared app-shell body) keeps re-deriving its own frame from its content's Auto Layout fitting size for as long as that content contains a **required equality** chain with no independent lower bound (cockpit-native-host-pages) - not just once at open. Confirmed live (`FM_DEBUG_HOSTEDITOR`-style probe: `setFrame`/`display:true` right after, then read `win.frame` again after a runloop tick): capping-and-centering the host editor's form column with a required `stack.widthAnchor == content.widthAnchor - 48` (paired with a `<=520` cap) made AppKit snap the *whole window* back to 568pt (the one width where that equality has zero slack) within one layout pass, even right after an explicit user resize to 1000pt - the window was effectively stuck. Swapping that one `==` for `>=`/`<=` inequalities (keep the `<=520` cap, position with `leadingAnchor >=`/`trailingAnchor <=`/`centerXAnchor ==` instead of a width tie) removed the trap entirely - verified holding any width the user drags to. This is *why* `HostEditorController`'s max-width-centered column uses inequalities, and it generalizes: any future standalone window with Auto-Layout-capped content needs the same inequality-not-equality shape, or it will silently refuse to stay resized. (4) An `NSScrollView`'s document view belongs width-pinned to `scroll.contentView.widthAnchor` (the clip view), never `scroll.widthAnchor` (the outer view) - caught in code review, not by inspection. With "Show scroll bars: Always" (System Settings, the default with a mouse attached), a non-overlay vertical scroller reserves a real ~15pt track that narrows the clip view without narrowing `scroll`'s own frame; pinning to `scroll.widthAnchor` lets the document view's trailing edge render underneath that track. `HostEditorController`, `FleetController`, and `ReviewController` (the last two fixed in cockpit-native-fixes5) all use `scroll.contentView.widthAnchor`; `SettingsController`'s otherwise-identical scroll setup still has the `scroll.widthAnchor` version and needs the same fix whenever it's next touched. (5) In a horizontal `NSStackView` row (icon + title/subtitle text + a trailing status pill and/or buttons), leaving every subview's compression resistance at its AppKit default (750, all equal) means a long title squeezes *every* subview roughly proportionally under narrow width, not just the title - and since the trailing pill/buttons are themselves small containers with edge-pinned labels, squeezing them below their fitting width can visually read as the badge "wrapping" even though nothing is a wrapping label (cockpit-native-settings-compact, `FleetController`'s PR/task rows). Fix: give the icon and every trailing control `.required` compression resistance (and hugging) so they never shrink, and give the title/subtitle text stack `.defaultLow` compression resistance so it's the one thing that truncates first. Generalizes to any row mixing fixed-size chrome with variable-length text. (6) `NSViewController.dismiss(_:)` is a documented no-op unless the view controller was presented via `presentAsSheet`/`presentAsModalWindow`/`presentAsPopover` (or has a `presentingViewController`) - for a plain top-level window whose `contentViewController` was just assigned directly (`HostEditorController`'s Save/Cancel/Delete, presented by `AppDelegate.presentHostEditor`), `dismiss(self)` silently does nothing. Fixed (cockpit-native-host-form-fixes) by closing the window directly (`view.window?.close()`) instead; verified live via `NSButton.performClick(nil)` on the located button plus a `win.isVisible` before/after check (no Accessibility permission needed - `performClick` runs the exact target/action path a real click does). Any future standalone-window view controller needs the same direct-close pattern, not `dismiss(self)`. (7) A second regular `NSWindow` opened while another app window is full screen docks into that same full-screen Space as a full-width tile by default (macOS's standard behavior for a second standard window) - this is what turned `HostEditorController`'s centered form back into a full-width layout, but only in full-screen mode. Fixed by setting `win.collectionBehavior = [.fullScreenAuxiliary, .moveToActiveSpace]` and `win.level = .floating` on the host editor's cached window in `presentHostEditor`, so it floats over the full-screen Space instead of tiling into it. Verified live via a temporary env-var-gated probe (`window.toggleFullScreen(nil)` then dump `win.frame` vs `screen.frame` - width stayed 640pt against a 1512pt screen, not stretched to match). Any future utility window opened over a possibly-full-screen main window needs the same `collectionBehavior`/`level` pair. (8) `NSVisualEffectView` with `.sidebar` material and `.behindWindow` blending mode - used for a real split-view sidebar, where it blends against the desktop through the window's own edge - renders an incorrect tint when used as a *full-size* destination or standalone window root, since `.behindWindow` blending composites against whatever is behind the *window* (desktop/other apps), not other content inside the same window (cockpit-native-theme-audit-review; same root cause independently hit and fixed for the Hosts sidebar in PR #18's Fix 6, then for the icon rail, `KeysSidebarController`, and `SnippetsController` in this task). Forcing the view's own `.appearance` does not fix it - only removing the vibrancy material does. Any full-size destination or standalone window's root should be a plain `NSView` with `wantsLayer = true` and a `HelmTheme`-derived `layer.backgroundColor`, exactly like `HostsSidebarController`/`FleetController`/`ConsoleController` already do; reserve real `NSVisualEffectView` sidebar material for an actual split-view pane with narrower, non-full-window geometry. (9) A plain `NSView()` used as an `NSScrollView`'s document view is **not flipped** by default, so y=0 is its *bottom*, not its top - while `FleetController`/`ReviewController` pin their `NSStackView` content to the document's *top* anchor (so the header is the visually topmost, highest-y arranged subview), a document shorter than the scroll's viewport (true before their background `gh`/Bitbucket fetch populates the section stacks) rests against the *bottom* of the clip view by default, leaving a blank gap the size of the shortfall sitting above the header - this is the "empty black area above the header for several seconds" bug (cockpit-native-loading-state). Confirmed live with a temporary geometry probe: with a plain `NSView`, the header sat at y=438 in a 668pt-tall viewport with 254pt of content (668-254=414, matching the gap exactly); swapping in `SettingsController`'s existing `FlippedView` (`override var isFlipped: Bool { true }`) pinned the header to y=24 and kept it there from frame 0 through 3s of simulated load. `SettingsController` already used this `FlippedView` + an explicit `scrollToTop()` in `viewWillAppear` (its own earlier Fix 4) - `FleetController`/`ReviewController` were simply built without carrying that pattern forward. Any new `NSScrollView`-backed destination needs the same `FlippedView` document view + `scrollToTop()` pair, or it will silently reproduce this bug the moment its content starts smaller than the viewport (e.g. during an async data load, or a genuinely short list). Follow-up (cockpit-native-fixes5): a captain report of the gap recurring specifically on the *first-ever* Overview visit after a cold launch could not be reproduced via extensive live instrumentation (geometry, `needsLayout`/`needsDisplay` flags, and appearance-transition timing all measured correct at every checked point, both on the first `isHidden`-toggle-triggered `viewWillAppear` and after the async `render()` grows the document height while already visible) - see that task's PR description for the actual probe transcripts. `viewWillAppear` and the end of `render()` in both controllers now force `view.layoutSubtreeIfNeeded()` immediately before `scrollToTop()` regardless, closing the two theoretical gaps the investigation could identify (a first-ever layout pass racing the automatic appearance notification; the scroll position never being re-pinned after the loading-skeleton's short content is replaced by full-height data) even though neither could be proven to be the captain's exact cause.

- **Diff (phase 2) is a direct Swift re-derivation of the reviewed HTML mockup's algorithm, not a port of its JS, and no third-party diff library** - `DiffEngine.swift` (pure logic, no AppKit import) does classic dynamic-programming LCS over lines, groups consecutive delete/insert runs into paired `changed` rows (remainder as pure add/remove against a blank counterpart), then a second LCS pass over whitespace-preserving word tokens for a changed row's two lines to know which words to highlight. `DiffResultView.swift` renders it as a plain `NSStackView` of two-column rows (not two synced `NSTextView`s - this app already had a working "rows in a flipped-document stack view" pattern for every other scrollable list, and it makes word-level highlighting a matter of `NSAttributedString` background-color runs on a label) - lines render single-line/non-wrapping so both columns of a row always stay the same height and therefore aligned. - **`fm/cockpit-tools-yaml-order-perf-fix` fixed a real captain-reported data-fidelity bug: Beautify alphabetized every mapping's keys instead of preserving the source document's order**, at every nesting level including the top-level document keys - root-caused to upstream `Yaml.dictionary`'s associated value being a plain Swift `[Yaml: Yaml]`, which has no defined iteration order (this used to be treated as a deliberate "deterministic output" trade-off in this file and in `Vendor/YamlSwift/README.md`; a real ~35-deployment manifest with a meaningful 10-key order per deployment showed it's a genuine bug, not a style choice). - **The same task also fixed a real, measured perf regression: `ToolsController.containerWidthMayHaveChanged` (added by `fm/cockpit-tools-page-ui-polish`, see below) forced a full Auto Layout resolve of the *entire window's* view hierarchy on every single window resize notification, unconditionally** - it's registered globally (`NSWindow.didResizeNotification`, `object: nil`) and used to call `view.window?.contentView?.layoutSubtreeIfNeeded()` before reading `gridContainer.frame.width`, regardless of whether the Tools page was even the visible destination. Every open Tools tab's full panel lives as a sibling of the landing-grid's `gridContainer` inside `pageStack` (`addTab` calls `pageStack.addArrangedSubview(instance.view)`), hidden but still fully participating in Auto Layout per this app's "hide, never rebuild" convention for permanently-mounted destinations - so this forced full-subtree resolve got measurably more expensive the more Tools tabs a captain had ever opened and left open, and that cost was paid on every window resize app-wide, not just while looking at Tools. **Measured live** (a temporary env-gated probe driving real `NSWindow.setFrame(_:display:true)` calls to simulate a live drag-resize, reverted before commit per "Verifying native UI bugs" below): with Console visible and 0 Tools tabs ever opened, live-resize cost ~3.6ms/frame; with Console visible and 20 Tools tabs open (hidden), the *same* resize cost ~20.2ms/frame - roughly a 5.6x regression paid on a page the captain wasn't even looking at, confirming the multi-session `ToolInstance` architecture (which lets tabs accumulate across a session) as the amplifying factor and the ui-polish-added resize handler as the actual trigger.
